### Принятые технические решения

1. **Схема создаётся скриптами, Hibernate в базе ничего не меняет** (`ddl-auto=none`).
   Проверка схемы средствами Hibernate (`ddl-auto=validate`) неприменима:
   PostgreSQL сообщает столбец, объявленный через домен, как отдельный тип
   (`DISTINCT`), и Hibernate отклоняет его как несовпадающий с `VARCHAR`.
   Поскольку домены — обязательное средство защиты от ошибок ручного ввода
   (требование «домены, маски, условия»), они оставлены, а контроль
   полноты схемы выполняет компонент `SchemaVerifier` при старте приложения.

2. **Домен проверяется при приведении значения к типу, то есть ДО срабатывания
   BEFORE-триггера.** Поэтому нормализация ввода не может выполняться доменом.
   Столбец `phone` переведён на обычное CHECK-условие: CHECK проверяется
   уже после триггера, и нормализация номера на уровне БД работает.
   Остальные реквизиты оформлены доменами.

3. **Триггеры обеспечивают целостность, недостижимую из приложения:**
   неизменность подписанных документов и журнала аудита (TR040),
   матрица допустимых переходов статуса документа, автоматическая
   регистрация номера документа, автопересчёт итогов и счётчиков
   листа ознакомления.

4. **Простая ЭП имитируется кодом подтверждения.** Реальный SMS-шлюз
   находится вне границ системы (документ «Видение» записки), поэтому
   код генерируется приложением и показывается в интерфейсе.

5. **Поиск по ФИО выполняется функцией `f_lower_ru(text)`.** Функция
   `lower()` сервера в локали `C` (в частности, в сборке PostgreSQL
   для Windows) не приводит кириллицу к нижнему регистру, поэтому
   поиск по фамилии не работал. Функция приводит кириллицу к нижнему
   регистру таблицей замен `translate()`, а латиницу — функцией
   `lower()`, и потому даёт одинаковый результат на любом сервере.
   Функция `IMMUTABLE`, проверка её работы включена в smoke-тест.

6. **Страницы ошибок имеют собственные адреса** `/error/403`,
   `/error/404`, `/error/500`. На `/error/403` ссылается настройка
   разграничения прав, поэтому без явного обработчика отказ в доступе
   превращался в страницу «не найдено».

7. **Удаление учётной записи — это обезличивание, а не `DELETE`.**
   Запись сохраняется, поскольку на неё ссылаются документы, этапы
   маршрута, листы ознакомления и журнал аудита. Персональные данные
   заменяются обезличенными значениями, роль снижается до EMPLOYEE,
   пароль сбрасывается, статус становится DELETED.

8. **Импорт выполняется построчно, каждая строка — в своей транзакции.**
   Ошибка в одной строке не откатывает уже загруженные строки;
   в отчёте по каждой некорректной строке указывается причина.

Трёхуровневая схема (TR020), соответствующая BCE-подходу из записки:

| Уровень | Реализация |
|---|---|
| Уровень представления | Thymeleaf-шаблоны + контроллеры Spring MVC (web/), бизнес-логики нет |
| Прикладной уровень | Сервисы Spring (service/) — DocumentService, RouteService, ValidationService, SignatureService, AcquaintanceService, NotificationService, AuditService, ReminderScheduler |

Сервисы прикладного уровня в точности соответствуют сервисам, названным в подразделе 3.6 записки — это позволит потом приложить реальные диаграммы классов без переделки.

## 3. Этапы работы

Каждый этап заканчивается работоспособным состоянием проекта и одним коммитом.

### Этап 1. Схема базы данных и доменная модель

**Что делаем**
- `sql/01_schema.sql` — источник истины по БД: 15 таблиц из таблицы 3.2 записки, 6 доменов (`d_email`, `d_inn`, `d_snils`, `d_personnel_number`, `d_full_name`, `d_doc_code`), CHECK-ограничения на перечисления, уникальные индексы, вычисляемые (GENERATED) поля, триггеры, материализованные представления, функции прогноза. В начале файла — проверка соответствия схемы: если структура таблиц расходится с ожидаемой (например, таблица создана автоматически Hibernate), схема пересоздаётся автоматически.
- `sql/00_reset.sql` — полный сброс схемы (нужен один раз, если старые таблицы мешают).
- 15 JPA-сущностей + перечисления (роль, статус пользователя, статус документа, действие/статус этапа, тип аудитории, события уведомлений).
- Репозитории Spring Data JPA.
- `DataSeeder` — начальное наполнение: организация, дерево подразделений, справочник должностей, справочник видов документов с JSON-шаблонами форм, демонстрационные пользователи всех четырёх ролей.
- `application.properties.example` — перевод реквизитов БД на переменные окружения (TR030: ключи не хранятся в исходном коде).

**Почему SQL-скрипт, а не только Hibernate:** требования к БД (домены, маски, триггеры целостности, вычисляемые поля, автопересчёт итогов, прогноз с доверительным интервалом) в JPA-аннотациях не выражаются. Скрипт — это и есть артефакт шага «Создание базы данных в СУБД» (п. 13 методики).

**Приёмка:** скрипт выполняется в Supabase без ошибок; приложение стартует, сид наполняет справочники; `app_users` совпадает с прежней таблицей по имени.

**Что делаем**

- Запрет изменения и удаления записей журнала на уровне БД (триггер) и на уровне приложения.

**Приёмка:** любое действие видно в истории; попытка изменить запись журнала невозможна; архивный документ не редактируется.

### Этап 10. Отчёты, аналитика и функции базы данных

Требования: FR180 + **все требования к БД из раздела «Требования к содержанию НИРС» (пункты a–g)** — это отдельная оцениваемая часть, ей нужно уделить должное внимание.

**Что делаем**

*Сторона приложения*
- `ReportService` — отчёты: реестр документов, сроки согласования, нагрузка на согласующих, просрочки, ознакомление с ЛНА (FR180).
- Выбор отчёта и периода, вывод на экран, выгрузка в XLSX/CSV.
- Пункт меню «Отчёты».

*Сторона БД — демонстрация требований a–g*

| Требование | Реализация |
|---|---|
| **a)** вычисляемые поля, использование в запросах | `GENERATED ALWAYS AS ... STORED` в `document` (число дней отпуска, признак подписи, признак архива) и `acquaintance_mark` (признак ознакомления); используются в отчётах и в `WHERE` |
| **b)** итоговые результаты с автопересчётом | материализованное представление `mv_stat_document_totals` (всего документов, по статусам, средний цикл) + триггер на `document`/`route_step`, пересчитывающий его при любом изменении |
| **c)** частные итоги с автопересчётом | материализованное представление `mv_stat_department_totals` (по подразделениям: количество документов, среднее время согласования, доля просрочек, охват ознакомлением) + тот же триггер |
| **d)** три лучших и три худших | представления `v_top3_approvers_load` / `v_bottom3_departments_duration` и функция `f_best_worst()` через `ORDER BY ... LIMIT 3` / `OFFSET` |
| **e)** выбор по ≥2 условиям из разных таблиц | отчёт «Просроченные документы по подразделению» — соединение `document` + `route_step` + `app_users` + `department` с условиями по подразделению, статусу и сроку |
| **f)** прогноз и доверительный интервал | функция `f_forecast_vacation_exhaustion()`: линейная регрессия (`regr_slope`/`regr_intercept`) по помесячному расходу отпускных дней, прогноз даты исчерпания баланса с 95% доверительным интервалом; выводится в отчёте по сотруднику |
| **g)** модифицированные запросы | CTE (`WITH ... AS`) на удаление, добавление и обновление: пакетный архив подписанных документов, массовое создание листов ознакомления, массовое обновление просроченных этапов — вызываются из сервисов, а не просто лежат в скрипте |

*Защита от ошибок ручного ввода*
- Домены: `email`, `inn` (12 цифр), `snils` (11 цифр), `phone` (+7 …) — маски через регулярные выражения.
- CHECK-ограничения на все перечисления, на размер файла, на `date_from <= date_to`, на `level >= 0`.
- Нормализация ввода через триггер (маска телефона, приведение email к нижнему регистру).

**Приёмка:** каждый пункт a–g имеет работающий сценарий в интерфейсе и воспроизводимый SQL-запрос; изменение данных в таблице мгновенно отражается в итогах.
