## Что сделано

PR закрывает **этапы 1 и 2** плана разработки ИС КЭДО (этап «Создание» по методике НИРС). Проектирование (этапы «Подготовка», «Анализ», «Проектирование») выполнено ранее — здесь реализуется программная часть: схема базы данных и аутентификация с разграничением прав.

Соответствие расчётно-пояснительной записке: раздел 3.7 «Проектирование структуры базы данных», таблица 3.2 (15 таблиц), подраздел 3.6 (классы трёх уровней), таблицы 2.2–2.4 (требования FR/TR и варианты использования).

### Этап 1. Схема базы данных и уровень данных

Схема создаётся скриптами из каталога `sql/`. Hibernate работает в режиме `ddl-auto=none` и в базе ничего не изменяет; полноту схемы при старте проверяет компонент `SchemaVerifier`.

| Объект | Состав |
|---|---|
| Таблицы | 15 — по таблице 3.2 РПЗ |
| Домены | 6 — `d_email`, `d_inn`, `d_snils`, `d_personnel_number`, `d_full_name`, `d_doc_code` |
| CHECK-условия | перечисления ролей и статусов, сроки, размеры файлов, маски ввода |
| Вычисляемые поля | `document.vacation_days`, `document.is_signed`, `document.is_archived`, `acquaintance_mark.is_acknowledged` (`GENERATED ALWAYS AS ... STORED`) |
| Триггеры | 12 — нумерация документов, иерархия подразделений, нормализация реквизитов, неизменность подписанных документов и журнала аудита, матрица переходов статуса, автопересчёт итогов и счётчиков |
| Материализованные представления | 2 — итоговые и частные итоги |
| Представления | 6 — просроченные документы, топ-3/худшие-3, сводка по листу ознакомления |
| Функции | 7 — прогноз, best/worst, модифицированные запросы (CTE), нормализация телефона, приведение к нижнему регистру с учётом кириллицы |

Требования к функциям базы данных (пункты a–g из «Требований к содержанию НИРС») закрыты:

- **a)** вычисляемые поля используются в запросах и отчётах;
- **b), c)** итоговые и частные итоги пересчитываются триггером при любом изменении данных;
- **d)** выбор трёх лучших и трёх худших экземпляров по показателю — `f_best_worst()`;
- **e)** выбор по не менее чем двум условиям из разных таблиц — `v_overdue_documents` (`document` + `route_step` + `app_users` + `department`);
- **f)** прогноз времени исчерпания остатка отпускных дней с границами доверительного интервала 95 % — `f_forecast_vacation_exhaustion()`;
- **g)** модифицированные запросы (CTE) на удаление, добавление и обновление — `f_delete_stale_drafts()`, `f_create_acquaintance_marks()`, `f_archive_signed_documents()`.

В приложении: 15 JPA-сущностей, перечисления доменной области, репозитории Spring Data JPA, `DataSeeder` (начальное наполнение справочников и демонстрационных учётных записей), `SchemaVerifier` (проверка состава схемы при запуске).

### Этап 2. Аутентификация и разграничение прав

- Вход по логину (адрес электронной почты) и паролю, **UC030**, **FR140**;
- пароли хранятся только в виде BCrypt-хэшей — **TR030**;
- защита от подделки межсайтовых запросов (CSRF) включена — **TR050**;
- разграничение прав по четырём ролям: сотрудник, руководитель, сотрудник ОК, администратор; разделы меню скрываются в зависимости от роли;
- форма входа, личный кабинет по макету «Мой кабинет» (рисунок 2.4 РПЗ) с виджетами и счётчиком непрочитанных уведомлений, список уведомлений, собственные страницы ошибок 403 / 404 / 500.

### ⚠️ Перед первым запуском

Схему базы необходимо создать вручную — Hibernate этого не делает. Выполнить **один файл** `sql/00_install.sql` в Supabase (SQL Editor) или PgAdmin: он самодостаточен и выполняет сброс, создание таблиц и создание всех объектов, а в конце печатает отчёт о составе схемы.

Модульные скрипты приведены в документации как отдельные шаги и остаются в репозитории:

```
sql/00_reset.sql      # сброс схемы
sql/01_schema.sql     # домены, 15 таблиц, индексы, вычисляемые поля
sql/02_objects.sql    # триггеры, представления, функции
```

`sql/00_install.sql` собирается из них скриптом `sql/build-install.ps1` — поэтому содержимое всегда синхронно. Скрипт `sql/99_smoke_test.sql` можно выполнить дополнительно: он проверяет 24 условия и откатывает транзакцию, не оставляя данных в базе.

### Проверка

- `sql/99_smoke_test.sql` — 24 из 24 проверок пройдены (в Supabase и на локальной БД): домены и маски отклоняют некорректный ввод, подписанный документ и записи журнала аудита защищены от изменения, недопустимые переходы статуса отклоняются, автопересчёт итогов срабатывает при изменении данных, аналитические функции возвращают корректный результат;
- вход в систему проверен по HTTP-сеансу с CSRF-токеном: неверный пароль отклоняется, верный открывает личный кабинет, меню скрывает недоступные разделы, выход из системы работает;
- приложение стартует и работает на PostgreSQL 15+ (Supabase) и на локальной БД.

### Принятые технические решения

1. **Проверка схемы средствами Hibernate (`ddl-auto=validate`) неприменима:** PostgreSQL сообщает столбец, объявленный через домен, как отдельный тип (`DISTINCT`), и Hibernate отклоняет его как несовпадающий с `VARCHAR`. Домены — обязательное средство защиты от ошибок ручного ввода, поэтому они сохранены, а контроль полноты схемы перенесён в `SchemaVerifier`.
2. **Домен проверяется при приведении значения к типу, то есть до срабатывания BEFORE-триггера.** Поэтому столбец `phone` переведён на обычное CHECK-условие: CHECK проверяется уже после триггера, и нормализация номера на уровне БД работает (`89161234567` → `+7 916 123-45-67`). Остальные реквизиты оформлены доменами.
3. **Реквизиты подключения к базе вынесены в переменные окружения** — в исходном коде ключи доступа не хранятся (**TR030**).
4. **Установка схемы — одним файлом `sql/00_install.sql`.** Раньше скрипты запускались по отдельности, и порядок запуска был источником ошибок: если `app_users` уже существовала со старой структурой, `CREATE TABLE IF NOT EXISTS` её пропускал, а следующий оператор падал на несуществующем столбце. Теперь файл самодостаточен, а `01_schema.sql` дополнительно сверяет фактический состав столбцов с ожидаемым и пересоздаёт схему при расхождении.
5. Простая электронная подпись на этом этапе не реализуется — она входит в этап 7.
