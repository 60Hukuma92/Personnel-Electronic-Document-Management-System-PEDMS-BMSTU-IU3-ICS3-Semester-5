## Что сделано

PR закрывает **этап 3** плана разработки ИС КЭДО (этап «Создание» по методике НИРС): раздел «Администрирование → Учётные записи», доступный только администратору.

Соответствие расчётно-пояснительной записке: таблица 2.2 (FR010, FR020, FR190), таблица 2.4 — вариант использования **UC040 «Управление учётными записями»**, требование **FR080** (журнал аудита) и **TR030** (хранение паролей в виде BCrypt-хэшей).

---

### UC040. Управление учётными записями

#### Реестр (FR010, FR190)

- поиск по ФИО, адресу электронной почты, табельному номеру и ИНН;
- фильтры по роли, статусу и подразделению; сводка по количеству записей в каждом статусе;
- сортировка по ФИО.

#### Карточка учётной записи (FR190)

Все реквизиты по FR190: ФИО, дата рождения, ИНН, СНИЛС, телефон, электронная почта, табельный номер, подразделение, должность, роль, статус учётной записи, дата создания и последний вход.

#### Жизненный цикл (FR020)

| Действие | Результат |
|---|---|
| Активация | учётная запись может войти в систему |
| Блокировка | вход невозможен, проверяется реальным HTTP-сеансом |
| Разблокировка | вход снова возможен |
| Сброс пароля | система формирует временный пароль и показывает его один раз |
| **Удаление с обезличиванием** | ФИО, ИНН, СНИЛС, дата рождения, телефон, табельный номер и адрес почты заменяются обезличенными значениями; роль снижается до EMPLOYEE; пароль сбрасывается; статус становится DELETED |

Запись физически не удаляется: на неё ссылаются документы, этапы маршрута, листы ознакомления и журнал аудита — удаление сломало бы целостность истории.

#### Загрузка из файла (FR010)

- форматы **XLSX** (Apache POI) и **CSV** (разделитель `;` или `,`, поддержка кавычек);
- распознавание наименований столбцов на русском и английском языках: ФИО, электронная почта, табельный номер, ИНН, СНИЛС, телефон, дата рождения, подразделение, должность, роль, пароль;
- распознавание роли по коду (`EMPLOYEE`, `MANAGER`, `HR`, `ADMIN`) и по русскому наименованию;
- **построчная проверка**: каждая строка проверяется отдельно и импортируется в собственной транзакции — ошибка в одной строке не откатывает остальные;
- отчёт: сколько строк загружено, сколько с ошибками и в чём именно ошибка по каждой строке;
- шаблон файла для скачивания.

#### Проверка вводимых данных

Проверка в приложении выполняется по тем же правилам, что и домены базы данных, — пользователь получает понятное сообщение сразу, а не сообщение СУБД:

| Реквизит | Правило |
|---|---|
| Электронная почта | `^[^@\s]+@[^@\s]+\.[^@\s]+$`, уникальность |
| ИНН | 12 цифр, уникальность |
| СНИЛС | 11 цифр или `XXX-XXX-XXX XX`, уникальность |
| Телефон | приводится к маске `+7 XXX XXX-XX-XX`, уникальность |
| Табельный номер | до 8 букв или цифр, через дефис — ещё до 8 символов, уникальность |
| ФИО | буквы, пробелы и знаки `-`, `(`, `)`, `,`, `.` |

### Сопутствующие исправления

1. **Страницы ошибок получили собственные адреса** `/error/403`, `/error/404`, `/error/500`. На `/error/403` ссылается настройка разграничения прав, поэтому без явного обработчика отказ в доступе показывался как «страница не найдена» (404 вместо 403).
2. **Функция `f_lower_ru(text)` в базе данных.** Функция `lower()` сервера в локали `C` (в частности, в сборке PostgreSQL для Windows) не приводит кириллицу к нижнему регистру, из-за чего поиск по ФИО не находил ничего. Теперь кириллица приводится таблицей замен `translate()`, а латиница — функцией `lower()`, поэтому поиск даёт одинаковый результат на любом сервере. Функция объявлена `IMMUTABLE`, её работа проверяется в `sql/99_smoke_test.sql`.
3. **Подключён `bootstrap.bundle.min.js`** и скрипт `static/js/pedms.js` (подтверждение опасных действий) — без этого не работали сворачиваемое меню, выпадающий список в шапке и подтверждение удаления.
